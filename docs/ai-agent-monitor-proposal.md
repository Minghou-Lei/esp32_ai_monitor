# AI Agent Monitor Proposal

## 文档定位

这份文档不是描述“当前已经实现了什么”，而是描述在当前本地工作树基础上，下一阶段可以如何把项目推进成更完整的 AI / 服务监控终端。

当前已实现的基础能力是：

- 统一配置模型
- 网络接入与门户状态机
- provider 轮询首版
- 板上主监控屏
- 本地配置网页
- BOOT 按钮配置入口

后续 proposal 应建立在这套基础之上，而不是回退到早期单功能诊断思路。

## 推荐产品方向

维持当前定位：

- 板子负责本地监控与配置
- 远端服务负责 AI / 业务执行
- 固件优先做好状态聚合、诊断、告警和少量控制

不建议把下一阶段主线改成“在板上直接运行完整大模型或重型 agent”。

## 下一阶段可交付

### 1. 更清晰的监控域模型

在现有 `provider_service` 基础上，把状态域进一步整理成：

- 设备网络状态
- 门户 / 首配状态
- provider / quota 状态
- 远端服务健康状态
- 最近告警与事件摘要

### 2. 多页面或多面板导航

在当前主监控屏基础上扩展：

- 总览页
- 网络诊断页
- Provider 状态页
- 配置入口页或配置页跳转提示

### 3. Provider 扩展

把当前单 provider 首版扩展成可演进框架：

- 保留统一配置模型
- 抽象 provider 状态转换
- 允许增加新的远端服务或账户监控源

### 4. 告警与控制动作

后续可加入：

- provider 异常提示
- 网络掉线提示
- 门户未完成提示
- 手动刷新或简单控制动作

## 不建议的方向

在当前阶段，不建议优先做这些事情：

- 重写整套板级驱动
- 绕开官方 `BSP`
- 在没有测试护栏的情况下大规模重构 Hosted 路线
- 把项目描述成“完整 AI 终端已经成型”

## 进入下一阶段前的前提

推进 proposal 前，建议先确保：

- 当前主监控屏稳定
- 配置网页能可靠保存关键配置
- provider 首版轮询在真实网络条件下可用
- Hosted / Remote 路线不再处于明显不稳定状态

只有在这些基础稳住之后，后续的产品层扩展才值得继续投入。
